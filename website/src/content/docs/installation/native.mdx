The native server runs on the host, so its terminals see your tools: `claude`, `git`, `gh` and the rest. termote
streams the terminal itself (PTY on Unix, ConPTY on Windows) into xterm.js in the PWA; there is no separate
terminal process to install.

## Prerequisites

termote needs one terminal backend: **tmux** (on Windows, **psmux**) or a running
**[Herdr](https://herdr.dev/#install)** server (see [Herdr Backend](#herdr-backend)); you do not need both. On Linux and macOS,
**[Zellij](https://zellij.dev/documentation/installation)** 0.45.0 or later is a third choice (see
[Zellij Backend](#zellij-backend)).

<Tabs>
  <TabItem label="Linux">

    ```bash
    # tmux
    sudo apt install tmux
    # or Herdr instead: see https://herdr.dev/#install
    # or Zellij 0.45+: see https://zellij.dev/documentation/installation
    ```
  </TabItem>
  <TabItem label="macOS">

    ```bash
    # tmux
    brew install tmux
    # or Herdr instead: see https://herdr.dev/#install
    # or Zellij 0.45+: brew install zellij
    ```
  </TabItem>
  <TabItem label="Windows">

    ```powershell
    # psmux: tmux-compatible multiplexer for Windows
    winget install psmux
    ```
  </TabItem>
</Tabs>

### tmux Configuration (Recommended)

With the tmux backend, for copy/paste to work with the keyboard toolbar buttons, add this to your `~/.tmux.conf`:

```bash
# Vi mode for copy: Space=start selection, Enter=copy
set-option -g mode-keys vi
# Mouse support (scroll, select) - toggle with Ctrl+b m
set-option -g mouse on
bind m set -g mouse \; display "Mouse #{?mouse,on,off}"
```

Apply the config:

```bash
tmux source-file ~/.tmux.conf
```

This enables: **Copy icon** → navigate → **Space** → select → **Enter** → **Paste icon**

<Aside type="tip" title="Copy to System Clipboard">
  With mouse ON, tmux captures mouse events. To copy to system clipboard:
  - **Hold Shift** while selecting text (bypasses tmux, uses terminal selection)
  - Or press **Ctrl+b m** to toggle mouse off temporarily
</Aside>

## Installation

<Tabs>
  <TabItem label="Linux / macOS">

    ```bash
    curl -fsSL https://termote.ohnice.app/install.sh | sh
    termote start
    ```
  </TabItem>
  <TabItem label="Windows (PowerShell)">

    ```powershell
    irm https://termote.ohnice.app/install.ps1 | iex
    termote start
    ```
  </TabItem>
</Tabs>

Then open http://127.0.0.1:7680 (Windows: http://127.0.0.1:7690). Pinning a version and the file locations are
covered in [Getting Started](/getting-started/).

Use `127.0.0.1` rather than `localhost`: termote does not listen on IPv6 `::1`, which a browser tries first for
`localhost`. Where that attempt hangs instead of failing (Windows with WSL set to `networkingMode=mirrored`), every new connection
waits for it, about 300 ms on each tab switch. A page opened through `localhost` shows a notice with a link to the
same page at `127.0.0.1`; an installed app has to be installed again from there.

## What `termote start` Does

<Steps>
1. **Picks the backend** the first time: Herdr when its server answers on its socket (`$HERDR_SOCKET_PATH`, else
   `herdr.sock` in Herdr's config directory: `$XDG_CONFIG_HOME/herdr`, or `~/.config/herdr`; on Windows
   `%APPDATA%\herdr`, reached as a named pipe), tmux (psmux on Windows) when it is installed. When both are there it asks, or, without a
   terminal to ask in, picks tmux and prints how to switch. When neither is there it stops with install hints.
   The choice is saved and not detected again unless you pass `--mux`. Zellij is never detected: choose it
   with `--mux zellij` or the menu (`termote` with no command).

2. **Creates the admin password** the first time (or with `--fresh`): type one, or press Enter to generate
   one. It is printed once; `termote show-password` shows it again later.

3. **Checks the port and Tailscale first.** If anything fails, a server that is already running is left
   running, so a mistake does not cut the connection you may be using.

4. **Registers `termote serve` with your service manager** and starts it (see the table below), waits until
   the server reports this version, then prints the URLs, the allowed host names and the credentials. It
   always warns when auth is off or LAN access is on.

</Steps>

| OS                                   | Service manager                                                          | Behaviour                                                                                                                                                              |
| ------------------------------------ | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Linux                                | systemd user unit `~/.config/systemd/user/termote.service`               | Restarted after a crash; tmux and its shells survive stop, restart and crash. Runs while you are logged in: `loginctl enable-linger $USER` keeps it running after logout and starts it at boot (`start` prints this hint) |
| Linux without user systemd (WSL2)    | Detached process with a PID file                                         | Not restarted after a crash or reboot; `start` says so. Run `termote start` again, or enable systemd in WSL (`[boot]` `systemd=true` in `/etc/wsl.conf`)                  |
| macOS                                | launchd agent `~/Library/LaunchAgents/app.ohnice.termote.plist`          | Restarted after a crash, started at login; tmux survives                                                                                                               |
| Windows                              | Scheduled Task `Termote` at logon, run hidden                            | No administrator rights needed. If policy refuses the task, a hidden launcher in the Startup folder is used instead (no restart after a crash then)                    |

The unit, plist or task never contains the password or any `TERMOTE_*` variable.

<Aside type="note" title="Windows">
  The Windows service setup is new in 1.0. Please report anything that does not work on
  [GitHub](https://github.com/lamngockhuong/termote/issues).
</Aside>

## Start Options

Every option is saved. A flag you leave out keeps its saved value, so `termote start` with no flags starts the
server exactly as last time. A boolean option is turned off with `=false`.

| Option                      | Description                                                            |
| --------------------------- | ---------------------------------------------------------------------- |
| `--port <port>`             | Port (default 7680; Windows 7690)                                      |
| `--lan[=false]`             | Listen on every interface instead of `127.0.0.1` only                  |
| `--tailscale <host[:port]>` | Publish over [Tailscale HTTPS](/installation/tailscale/) (default 443) |
| `--no-tailscale`            | Stop publishing over Tailscale                                         |
| `--no-auth[=false]`         | Disable the login                                                      |
| `--mux <tmux\|herdr\|zellij>` | Terminal backend (default: detected the first time; zellij: Linux, macOS) |
| `--allow-host <name>`       | Allow another `Host` header name (repeatable, no wildcard)             |
| `--remove-host <name>`      | Remove an allowed name (repeatable)                                    |
| `--allow-local-user <name>` | Let another OS user of this machine connect, e.g. a reverse proxy      |
| `--remove-local-user <name>`| Stop letting that user connect (repeatable)                            |
| `--allow-path <dir>`        | Offer a folder in Files, under [Places](/usage/files-changes/#places) (repeatable) |
| `--remove-path <dir>`       | Remove an allowed folder (repeatable)                                  |
| `--allow-herdr-no-auth`     | Required together with `--mux herdr --no-auth`                         |
| `--user <name>`             | Login username (default `admin`; shared with the container)            |
| `--fresh`                   | Set a new password                                                     |

```bash
termote start --lan                  # also reachable from the LAN (saved)
termote start                        # same options as last time
termote start --lan=false            # back to this machine only
termote start --allow-host box.local # accept another host name
termote start --remove-host box.local
termote start --allow-path ~/notes   # edit a folder outside the pane in Files
termote start --fresh                # new password
termote start --user alice           # log in as alice instead of admin
```

The allowed host names are always loopback, the Tailscale name, the `--allow-host` names, and with `--lan` the
address a request arrived on (so it keeps working when the LAN IP changes). A request for any other name gets a
403 that names the `termote start --allow-host <name>` to run.

### Other users of this machine

On Linux and Windows the server refuses every connection made from this machine by another OS user,
whether it goes to `127.0.0.1` or to the machine's LAN address: your own user, root/SYSTEM and the users you
allow are let in. A reverse proxy that runs as its own user (nginx as `www-data`, Caddy as `caddy`) needs
allowing; the server log names the command when it refuses one. On Windows a proxy that runs as a service
is let in when it is the service's own process and your user cannot read its token (one whose token your
user can read counts as its account, to allow like any other user); one that a wrapper such as NSSM or
WinSW starts is refused: register the proxy itself as the service, or run it as your user. A service
your user cannot open at all is refused too: for a standard user that includes `tailscaled`, so
[`--tailscale`](/installation/tailscale/) does not work on native Windows.

```bash
termote start --allow-local-user www-data
termote start --remove-local-user www-data
```

macOS does not check the user of a connection, and WSL 2 lets every Windows user in. What else is left open:
[Security Model](/usage/security/).

<Aside type="caution" title="Give Termote a host name of its own">
  Browsers send a site's cookies to every port of its host name, so another web service on the same name (another
  port on the same server, another app on the same domain) receives Termote's session cookie whenever you open
  it, and with it a signed-in terminal. On a server that runs anything else, reach Termote under a name only it
  answers on: a Tailscale name, or a name of its own such as `termote.example.com`. Log out from the **More** menu
  on a device you no longer use.
</Aside>

## Herdr Backend

Linux, macOS and Windows can drive Herdr workspaces instead of tmux (psmux on Windows). Herdr must be installed on this host
([install Herdr](https://herdr.dev/#install)); Termote talks to its socket, and starts `herdr server` itself when it is not running. When Herdr is running at the first `start` it is picked for you; otherwise:

```bash
termote start --mux herdr
```

<Aside type="caution" title="Herdr behavior differs from tmux">
  - Selecting a tab or pane on the PWA does **not** change what is shown on the Herdr desktop
  — it only changes which pane the client streams. There is no "show on desktop" button.
  - Each pane gets an agent-status badge (idle/working/blocked/done) refreshed at most once
  per the configured poll interval; it is not pushed instantly.
  - Herdr need not be running. When you open the page and nothing answers on its socket, Termote starts `herdr server` in
  the background; the page connects within a few seconds (the first 15 s after the server starts are left to you or to a service
  that starts Herdr, and after a failed start Termote waits 30 s, doubling to 10 minutes). Devices that can only view never
  start it. There is no option to turn this off.
  - A Herdr started this way keeps running after `termote stop`, `restart` and `update`, like tmux, and `termote stop` does not stop it.
  While a full page is open, a Herdr stopped with `herdr server stop` is started again. Its output goes to `herdr-autostart.log`,
  shown by `termote logs` and `termote logs follow`, not by `termote logs server`.
  - Its panes get the service's environment: variables set by a login session or terminal (`SSH_AUTH_SOCK`,
  `DISPLAY`/`WAYLAND_DISPLAY`, sometimes `DBUS_SESSION_BUS_ADDRESS`, `COLORTERM`) may be missing, while variables from your shell's rc
  files are there. Start Herdr yourself from that session to keep them.
  - On a machine where Herdr is installed but not running, with no tmux or psmux, the first `termote start` still says no backend is found:
  run `termote start --mux herdr`.
  - This is the Herdr on your host. The container runs its own Herdr instead, see
  [Container Installation](/installation/docker/#terminal-backend).
  - `--mux herdr --no-auth` is refused unless `--allow-herdr-no-auth` is also given: Herdr
  exposes every workspace on the host, not just the pane the PWA is showing, so running it
  without a password needs an explicit opt-in.
</Aside>

## Zellij Backend

Linux and macOS can drive your [Zellij](https://zellij.dev/documentation/installation) sessions instead of tmux.
It needs Zellij 0.45.0 or later (tested with 0.45.1); `start` checks that `zellij` is on your PATH and its version.
Zellij is never picked for you:

```bash
termote start --mux zellij
```

A group is a Zellij session, a tab a Zellij tab and a pane a terminal pane (plugin panes are not shown). Every
running session of yours is listed, as with tmux. `start` passes `ZELLIJ_SOCKET_DIR`, `XDG_RUNTIME_DIR` and, on
macOS, `TMPDIR` from your shell to the service, so it sees the same sessions as that shell; run `termote start`
from the shell whose sessions you want.

<Aside type="caution" title="Zellij behavior differs from tmux">
  - The terminal is a real Zellij client: Zellij draws its own tab bar and status bar, and a tab takes the size
  of the smallest client viewing it.
  - Selecting a tab on the PWA does **not** move your own Zellij client; each device selects its own tab.
  - Termote's client is in Zellij's locked mode, so the toolbar's Ctrl keys (Ctrl B, P, N, T, O, Q...) reach the
  pane. Your own locked-mode bindings still act (the default config's Ctrl g unlocks).
  - There is no server-side scrolling: the mouse wheel scrolls through Zellij itself, for every client viewing
  that pane. Select text still shows the pane's history.
  - A new tab needs a client attached to the session (a terminal, or Termote showing it); otherwise you see
  "open this Zellij session in a terminal (or in Termote) before adding a tab".
  - Closing a session from Termote deletes it: Zellij cannot resurrect it.
  - On Windows, native `--mux zellij` is refused; use `termote container up --mux zellij`, see
  [Container Installation](/installation/docker/#terminal-backend).
</Aside>

## Managing the Server

```bash
termote status          # what the running server reports (version, backend, pid, Via)
termote signins         # browsers signed in with the password; signins revoke <id>|--all
termote stop            # stop it; it starts again at the next login
termote restart         # stop and start with the saved options
termote logs            # recent lines of every log
termote logs server     # server log only
termote logs follow     # tail live (Ctrl+C to stop)
termote logs clean      # delete the log files
termote show-password   # print the saved username and password
```

The CLI talks to the server over a socket only your user can open (`~/.local/state/termote/run/<port>.sock`,
a named pipe on Windows), without sending the password; `termote status` shows `Via: socket`. Against the
container or an older server it uses `127.0.0.1` and the saved password (`Via: TCP`), except the native server
on Windows, which gets the password over its pipe only (`termote status` then says the pipe did not answer).

The service runs `termote serve`, which reads the saved config. Once a config file exists, `TERMOTE_*`
environment variables are ignored, and `serve` removes them from its environment so no terminal inherits one.

## Updating

```bash
termote update                   # newest stable 1.x release
termote update --version 1.0.1   # a specific version
termote update --version 1.13.0-rc.1  # a pre-release, only when named
termote update --force           # reinstall the current version
```

`update` downloads the release and checks its `.sha256` and, from 1.10.0 on, the release signature: an archive
the Termote release key did not sign is refused even when its checksum matches. It installs it beside the current version, switches to it,
restarts the service and waits until the server reports the new version and keeps answering. If it does not, it
switches back to the previous version and restarts that one. The current and the previous version are kept; your
config and the service registration do not change. It works when typed inside a Termote pane.

`update` refuses to run from a git checkout (use `git pull && make build` there) and for a binary that the
installer did not put in place.

## Uninstall

```bash
termote uninstall          # keeps your config, saved password, logs and deleted files
termote uninstall --purge  # removes them too
```

This removes the service registration, Termote's Tailscale mapping, the `termote` command, the install root and
the images you uploaded from the app (a cache). Your config (`~/.config/termote`) and logs (`~/.local/state/termote`)
stay, so a reinstall keeps your password and your devices stay signed in; `uninstall` prints both paths. On Windows,
`%APPDATA%\termote` and `%LOCALAPPDATA%\termote\state` stay. Add `--purge` to remove them as well; the interactive
menu asks.

The files you deleted from the Files view stay as well (they move to a trash next to the uploads, such as
`~/.cache/termote/trash`), since they are your files and not a cache; `uninstall` prints the folder. `--purge`
removes it too.

On Windows, the files of the running `termote.exe` are removed a moment after the command exits.

## Prevent macOS Sleep

macOS automatically sleeps after inactivity, disconnecting remote terminal sessions. Use `caffeinate` to keep the machine awake while Termote is running:

```bash
# Prevent system sleep (runs until you press Ctrl+C)
caffeinate -s

# Or run in background
caffeinate -s &

# Stop background caffeinate
pkill caffeinate
```

<Aside type="tip">
  Use `caffeinate -s` (system sleep only) instead of `-d` (display sleep) — you
  don't need the display on for remote access.
</Aside>

## Troubleshooting

### Quick Diagnostics

```bash
termote status          # is it running, which version and backend
termote logs server     # last server log lines
```

### Common Issues

| Issue                                    | Solution                                                                                    |
| ---------------------------------------- | ------------------------------------------------------------------------------------------- |
| `termote: command not found`             | Open a new terminal, or add `~/.local/bin` to your PATH as the installer printed             |
| No terminal backend found                | Install tmux (Windows: `winget install psmux`) or Herdr, then `termote start --mux herdr`     |
| `zellij not found` / `is too old`        | Install Zellij 0.45.0 or later, then `termote start --mux zellij`                            |
| Zellij sessions missing                  | Run `termote start` from the shell that sees them (`zellij list-sessions`); EXITED ones are not listed |
| `zellij_version_mismatch` after an upgrade | Restart the Zellij sessions of the old version (or Termote)                                |
| `zellij_socket_dir`                      | The Zellij socket dir is not private to you (the log says why): `chmod 700` it, or set `ZELLIJ_SOCKET_DIR` to a private dir |
| Port in use                              | `start` names the port; stop the other program or choose `termote start --port <port>`      |
| Host rejected (403)                      | Run the `termote start --allow-host <name>` the error names                                  |
| Reverse proxy gets no answer             | The log shows `local-user-refused`: run the `termote start --allow-local-user <name>` it names |
| Saved password cannot be decrypted       | The `secret` file was removed or replaced: `termote start --fresh`                           |
| Stops when you log out (Linux)           | `loginctl enable-linger $USER`                                                               |
| Not running after a reboot (WSL2)        | No user systemd there: `termote start` again, or enable systemd in WSL                       |
| No sessions, `mux command failed` (Windows) | `psmux list-windows -t main` prints nothing while `psmux ls` lists it: a filter is intercepting localhost traffic. In AdGuard, turn off "Filter localhost" |
| Stale PWA cache                          | More (⋯) menu → "Clear cache & reload" to refresh (it also signs out and drops unsaved file text)                                                |
