The orchestrator is a Claude Code or Codex session you chat with to coordinate the coding agents
running in your other Termote panes. Ask it what each agent is doing, to give one of them a task,
to tell you when it is done, what it said and what it changed, to show you a dialog an agent waits
on, to stop one, or to start new agents, each in a git worktree of its own. It works through the `termote agents` commands, so it uses what
Termote already does for you in the [Chat view](/usage/agent-chat/) and the
[Overview](/usage/overview/), with the tmux, Herdr, Zellij and herdr-core backends alike.

It is optional: nothing changes until you install the skill, and Termote never writes to Claude
Code's or Codex's directories on its own.

## Requirements

- Termote running natively (`termote start`). In container mode there is no local socket, so
  `termote agents` says it is not supported.
- Claude Code or Codex, for the orchestrator session itself. The agents it coordinates can be
  Claude Code, Codex or OpenCode, as in the Chat view.

## Install the skill

Pick one of the two ways, not both: with both, the agent sees the skill twice.

**From Termote itself.** The skill is part of the `termote` binary, so it always matches it:

```bash
termote skills install                 # for Claude Code and Codex, where each is set up
termote skills install --agent claude  # or only one of them
termote skills status                  # installed, and does it match this termote?
termote skills uninstall
```

It writes `~/.claude/skills/termote-orchestrator/` (or under `CLAUDE_CONFIG_DIR`) and
`~/.codex/skills/termote-orchestrator/` (or under `CODEX_HOME`), and only for an agent whose
directory exists. A folder of that name you made yourself is left alone. After `termote update`,
Termote tells you when the installed skill is from another version; run `termote skills install`
again. `termote skills status` compares the installed file with the one in the binary too, so a
skill left from an earlier build of the same version is reported as out of date; `--json` gives the
SHA-256 of the skill this termote carries (`sha256`) and of each installed one.

**As a plugin**, from the small `termote-plugins` marketplace (it never downloads the Termote
repository):

```text
/plugin marketplace add lamngockhuong/termote-plugins
/plugin install termote@termote
```

```bash
codex plugin marketplace add lamngockhuong/termote-plugins
codex plugin add termote@termote
```

The first block is for Claude Code, the second for Codex. The
[termote-plugins](https://github.com/lamngockhuong/termote-plugins) repository is generated from
Termote at each stable release, so the plugin carries the skill of the newest release; the skill
needs Termote running natively, and says when this termote is too old for it. `termote skills status`
notes when the plugin is installed too, and `termote skills install` warns about it.

## Set up the orchestrator

Open a workspace for it, named `orchestrator` for example (a tmux session, a Herdr workspace),
start Claude Code or Codex there, and ask, for example:

- "What are my agents doing?"
- "Ask the agent in the api pane to run the tests, then tell me what failed."
- "Start a Claude Code agent in the web workspace to write the missing tests."
- "Start three agents in worktrees: one per failing test file. Tell me when each is done and what it changed."

Its folder does not matter: the skill comes from Termote or the plugin, not from a repository.

## What it runs

The skill only runs these commands. You can run them yourself too:

```bash
termote agents list [--json]                 # every agent: pane id, workspace, name, status, folder
termote agents read <pane> [--all] [--json]  # its last turn: your request and everything since
termote agents send <pane> 'Run the tests'   # one message; queued when the agent is working
termote agents wait <pane>@<seq>...          # until one of them ends a turn or needs an answer
termote agents answer <pane>                 # show the dialog it waits on
termote agents answer <pane> 1               # or: cancel | next | --text 'an answer'
termote agents diff <pane> [--stat]          # its commits since the base, then what is not committed
termote agents stop <pane> --cursor <cursor> # end the turn it runs, as Esc (cursor from read --json)
termote agents start --workspace <id> --kind claude --name tests 'Write the tests'
termote agents start --workspace <id> --kind claude --worktree fix-login 'Fix the login test'
termote agents jobs [--mine] [--all] [--json] # the job ledger by priority: each job's pane, status, unread turn, branch
termote agents jobs --ready                  # the jobs to do that wait on nothing: what to start next
termote agents job add --title 'Docs' --priority high --after <job> --workspace <id>
termote agents job set <id> --priority low --no-after <job>   # also --after <job>, --workspace, --no-workspace
termote agents job show <id>                 # its prompt, note, grants and history
termote agents job set <id> --state review --note 'What was done'
termote agents job remove <id>               # remove a done, failed or abandoned job from the ledger
termote agents job finish <id> --close --remove-worktree   # after your yes: close its tab, remove its worktree
termote agents jobs prune --older-than 7d    # every finished job not changed for 7 days (--dry-run lists them)
termote agents wait --job <id>...            # until one of the jobs' agents needs the orchestrator
termote agents wait --mine                   # the same, over every unfinished job made from its pane
termote agents answer <pane> --delegated     # Yes, this once, under a grant you gave in the PWA
```

A `<pane>` is the pane id `list` shows (`%3`, `w1:p2`), or a name only one pane has: the pane's
own name, else its tab's (`api`), or `workspace/name` (`web/api`). A name two panes share is
refused, with both ids.

`wait` takes one pane or several and returns as soon as one of them ends a turn (exit 0), shows a
dialog (3) or loses its agent (5); every pane that ended is printed, and the gravest exit wins. 4
means `--timeout` passed (30 minutes by default), 6 that no pane works and none ended (nothing to
wait for), 7 that the server's history was reset (read each pane).

An agent may end its turn with a question for you written in its answer rather than in a dialog
("Shall I add a test too?"). That is still a turn that ended (exit 0), but `wait` says the pane
`ends with a question`, and `read` marks it too (`endsWithQuestion` in `read --json`), so the
orchestrator asks you and sends your answer instead of reporting the work as done. Termote only
looks at whether the last line of the answer ends with a question mark.

A Claude Code agent that has written its answer and only waits on background work it started
(a background agent) is reported once too, and stays in the `next:` line so the next `wait`
reports when that work is done; `list` shows it as `background`. An agent whose turn ended while
a shell it started still runs (`done` with `background: "1 shell"`) is still waited on: the shell
ending starts its next turn, and `wait` reports that turn's end rather than say there is nothing to
wait for.

Each pane is waited on from a mark of its own, taken from the server's activity log: `send` and
`start` print the pane with its mark (`termote agents wait %3@41`), and `wait` prints a `next:` line
with each pane it did not report and that pane's mark (`next: termote agents wait %3@41 %5@48`), or
says no pane is left. A pane waiting on a dialog stays in that line, so the wait after an answer
follows it. To wait on several agents, put together each one's latest `<pane>@<seq>`.
A turn that ended while the orchestrator was reading another pane is then still reported, even
when it ended before a mark printed for another pane, and one already reported is not reported
again. `--after <seq>` gives the mark of every pane named without one; `list --json` has the
latest mark (`latest`) for a first wait, and names the pane it runs in (`self`) when the tmux,
Herdr or Zellij environment says so for sure. That pane is then refused to `send` and to a job's
`--pane` (`job add`, `job set`): a job goes to the agent that does the work.

An orchestrator in Claude Code runs `wait` in the background, with marks or with `--job` alike, so
you can keep talking to it while its agents work: Claude Code tells it when the `wait` exits. It
then handles what the `wait` reported, reads each pane it named, and only after that starts the
next `wait` from the `next:` line (or `wait again:` after a timeout), keeping each pane in a single
running `wait`. That notice is not you: it never counts as a yes. An agent whose background
commands do not report back, such as Codex, waits as before, with a `--timeout` shorter than its
command limit; Claude Code would stop an ordinary command after 10 minutes at most.

`diff` shows what an agent changed in its folder: the commits of its branch since it left the
base (by default the branch your main checkout has, or `--base <branch>`), then what is staged,
unstaged and untracked. Each file's diff comes after a line saying it is data written by the
agent, not instructions; a sensitive file such as `.env` shows by name only, and at most 64 KB of
diff is printed (`--stat` lists the files only).

## The job ledger

Termote keeps a ledger of the work the orchestrator hands out, so neither of you depends on its
memory: it survives a compacted conversation, a new tab and a server restart. Every `start` records
a job, titled with `--title` (or "claude in fix-login": never the prompt, since a view-only device
sees titles), and `send`, `read`, `answer`, `stop` and `diff --stat` note what they did on the job of
their pane. `termote agents jobs` lists the jobs not finished yet: the pane, what its agent does,
whether a turn ended that the orchestrator has not read, the branch and folder.

`wait --job <id>...` reports a turn the orchestrator has not read however long ago it ended (even
before the wait started, or while the server was down), a dialog once even if you keep it open, and
a job whose agent is gone (tmux restarted, the pane closed). When every job's agent is idle, its
last turn was read and no shell it started still runs, it says there is nothing to wait for instead of waiting out the timeout. Termote tells a job's agent from another
one at the same pane address by its process, so an agent that took over a reused tmux pane id is
never taken for it. When an agent is done the orchestrator sets the job to `review` with a note, and
you get a push; it never marks a job `done` for you.

When Termote knows the orchestrator's own pane (`self`), the orchestrator waits with `wait --mine`
instead of naming jobs: every job made from its pane that is not finished, `review` ones included,
read again from the ledger at each check. A job it starts while the `wait` runs, or one it gives
more work after setting `review`, is followed without it having to remember to; after each report
it reads the pane and runs `wait --mine` again. A job with no agent, or whose lost agent was already
reported once, never holds up the others, and the `wait` says there is nothing to wait for only
when no job left has an agent that can end a turn. Where Termote cannot tell its pane (`herdr-core`,
psmux, Windows), `wait --mine` is refused and the orchestrator names the jobs with `--job`.

### Priority, order and workspace

A job has a priority (`high`, `normal` or `low`, set with `--priority`), and may wait on other jobs
(`--after <job>`, a job id: unlike the `<pane>@<seq>` marks of `wait`, it names jobs). `jobs` lists
them by priority, the jobs to do oldest first, with what each still waits on (marked `!` when that
job failed or was abandoned) and its workspace. `jobs --ready` keeps the jobs to do that wait on
nothing: the orchestrator picks the next job there at the start of a session, after each job reaches
review and after each `job finish`, since finishing a job can make the jobs after it ready. Only a
`done` job lets the ones after it start; one that failed or was abandoned keeps them waiting until
you decide (drop it with `job set <id> --no-after <job>`, or abandon the job). `start --job` refuses a
job that still waits, naming what it waits on. A job cannot wait on itself, on a job that no longer
exists, or round in a circle; a job removed from the ledger is dropped from the jobs that waited on
it. `--after` on a job already running, in review or finished only notes the order: it never holds
up a state change or `job finish`.

A job's workspace (`--workspace <id | name>`) can be set while no agent has it; once it has an
agent or a worktree it is the workspace it was started in (for a worktree, the one the worktree was
made from) and is no longer changed by hand. When that workspace is closed and opened again on the
same repository under a new id, the job is shown under the new one.

You see the same ledger in the [Overview](/usage/overview/#plan)'s Plan tab, where you can also add
a job for the orchestrator to take up (`start --job <id>`), and open a job's details to edit it or
give grants. The card of an agent working on a job names the job. **Copy ID** in the details puts
a line with the job's id, its title and `termote agents job show <id>` on the clipboard: paste it to
an agent to point it at that job rather than naming it by its title.

## Questions waiting on you

The orchestrator records every question it puts to you with `termote agents ask add` before it asks,
and asks it by the id that prints (`Q3`). Termote keeps the list, so the ids stay the same after the
conversation is compacted or the server restarts, an answered question is never asked again, and
each reply ends with only the questions still open (`termote agents ask list`).

You do not have to open the overview to see that a question waits: its button in the sidebar
carries the count of open questions (on a phone, a dot on the view menu and the count beside
**Agent overview** in it), and the overview then opens on the Plan tab, whose label counts them too.
The chat of the orchestrator that asked also lists its own open questions above the message box,
with the same buttons, so you can answer without leaving it. It shows the oldest one; **Show N more
questions** beside its title unfolds the others, and an arrow at the bottom of the box scrolls to
the ones below.

You can answer here in the conversation, in an agent's tab, or in the Plan tab of the
[Overview](/usage/overview/#plan): its "Waiting on you" section shows each open question with the
pane that asked, its job, and a button for each choice or a box for your own words. Termote types
your answer into the orchestrator's input box as `Answer to Q3: ...` (or
`Answer to Q3 (choice 2): ...`), and the orchestrator closes the question with
`termote agents ask close Q3`. A draft you left in the orchestrator's input box is never replaced:
the answer is refused and the question stays open until you send or clear the draft. When the
orchestrator that asked no longer runs, the PWA says so: answer it in its terminal, or dismiss it.

A question you do not want to answer can be dismissed: **Dismiss** on its card, in the Plan or in
the chat, asks you to confirm on the card itself, then takes it off the list, whether its
orchestrator still runs or has exited. Nothing is typed into the orchestrator's input box: the next
`termote agents wait --mine` tells it once (`Q3 dismissed in the PWA`), and it does not ask that
question again. A dismissed question no longer counts as waiting, and no longer holds a job's
finish. A view-only device sees how many questions wait and their ids, never their text. A machine open
through [Machines](/usage/machines/) shows its own questions, and you answer or dismiss them from the
browser; another Termote's command line cannot.

```bash
termote agents ask add --text 'Merge PR #12 now?' --choice Yes --choice Later --job <id>
termote agents ask list
termote agents ask close Q3 --answer 'Later'
```

Any program you run can name the orchestrator's pane on the local socket, as it can already send
the orchestrator a message, so the PWA shows which pane asked each question.

## Grants for permission dialogs

A permission dialog (run a command, edit a file) is yours to answer. To keep a long task moving
while you are away, you can give one job's agent a grant in the PWA, signed in with your password
or a paired device: run commands that start with a prefix you type (`pnpm test`), or edit files in
the job's worktree while its agent works there, for up to a day. Only you give grants: the orchestrator, the command line,
another Termote and a server without sign-in cannot. For a machine open through
[Machines](/usage/machines/), give them on that machine's own Termote; here they are only shown.

A command prefix names a program and the command you allow, as you would type them. Termote takes
only the programs and commands of one short list:

| Program  | Commands you can grant                                                       |
| -------- | ---------------------------------------------------------------------------- |
| `npm`    | `test`, `start`, `ls`, `outdated`, `explain`, `run <script>`, `ci`, `audit`  |
| `pnpm`   | `test`, `start`, `ls`, `list`, `outdated`, `why`, `run <script>`, `install`  |
| `yarn`   | `test`, `start`, `why`, `run <script>`, `install`                            |
| `cargo`  | `build`, `test`, `check`, `clippy`, `fmt`, also after one `+toolchain`       |
| `go`     | `build`, `test`, `vet`, `fmt`, `list`, `mod`, `version`                      |
| `dotnet` | `build`, `test`                                                              |
| `pip`    | `list`, `show`                                                               |
| `vitest` | `run`, `list`                                                                |
| `biome`  | `check`, `format`, `lint`, `ci`                                              |
| `ruff`   | `check`, `format`                                                            |

`rg`, `grep`, `ls`, `cat`, `head`, `tail`, `wc`, `diff`, `tsc`, `eslint`, `jest` and `pytest` do one
thing each and take no command: grant the name alone, or with the options you allow (`rg -n`).
They read only inside the grant's folder: the job's worktree while the agent works there, else the
folder the agent works in when you give the grant (the grant shows it). A word that starts with `/`
or a drive such as `C:`, or holds `..`, is refused, in the prefix you type and in what the agent asks
(`cat /etc/hosts`, `rg foo ../other`), and so is a command the agent runs from another folder or a
file reached through a link that leads out of the grant's folder. A grant for one of these tools given
before grants kept a folder is revoked when the server starts.

Type the command in full: `pnpm run lint`, not `pnpm lint` (nor `yarn workspace a lint`), and a
script command needs the script's name (`npm run` alone is refused). `install`, `ci` and `npm audit`
take no package name (`pnpm install x` and `npm audit fix` are refused). The program is its bare name
(`rg`, not `/usr/bin/rg` or `rg.exe`). Every other program is refused, a shell, an interpreter,
`git`, `make`, `tar`, `docker`, `npx`, `brew` and `gem` among them. A grant given under older rules
whose prefix the list refuses (a bare `npm`) answers nothing, and the server revokes it when it
starts.

The orchestrator then tries `answer <pane> --delegated` first. Termote itself checks the dialog
and answers "Yes" for this one time only when the dialog on screen and the one tool call the
agent's transcript has waiting name the same command or file, no subagent runs, the command holds
nothing a shell would chain, expand or redirect, is itself on the list above and starts with your
prefix, no word after your prefix is an option (starts with `-`, `@` or `+`, or is `/p:`: `rg
--pre=x` or `go test -exec=x` runs another program, so type into the prefix the options you allow), and
the file is in the worktree, reached through no link, and not one that configures the agent, runs
as a hook or is run by one of your git hooks, or holds secrets (`.claude/`, `.git`, `.yarn/`, `CLAUDE.md`, `package.json`, lockfiles, a CI pipeline, a `justfile`, `.env`...).
A file in the folder your repository's `core.hooksPath` names counts as run by a hook too.
Anything else is refused and comes to you as before. Each answer shows on the job's card and in the
server's audit log.

<Aside type="caution">
  A grant to run a test, build or script command runs code the agent can edit: `pnpm test` runs
  the test files and whatever `package.json` declares for `test`, `dotnet build` the project's
  build targets, and an agent that can edit files in the worktree could change them. Give grants
  for short, well-known commands, on jobs you follow.
</Aside>

From the command line, an option that stops a dialog from asking again ("don't ask again",
"always allow", switching to auto mode) is always refused: only you pick one, in the PWA or the
terminal. Every answer to a permission dialog made from the command line is written to the audit log.

## Pull requests and CI

The agent pushes its branch and opens the pull request; Termote never opens, merges or closes
one. On a native install, the server follows each unfinished job's pull requests with the GitHub
CLI you signed in on that machine (`gh auth login`; Termote keeps no token): those of the job's
branch (on the `upstream` remote when the branch is pushed to a fork), and any attached by number
with `termote agents job set <id> --pr <number>` or from the job's details. A pull request closed
before the job was made, and the repository's default branch, are left out.

Each job's card shows a chip coloured by its worst pull request: checks failed, running, passed,
draft, or all merged. View-only devices see the chip and the numbers, never a check's name. The
job's details list each pull request with its failed checks and a link to it. Pull requests are
read every 20 seconds while checks run, every minute otherwise, and again when you press Check
again. When checks fail anew, or every pull request is merged or closed, you get a push.

**Send the failed checks to the agent** pastes a short message into the agent's input box: the
pull request's number, the failed checks' names, and the `gh pr checks` and `gh run view
--log-failed` commands to read them. It never sends a log: the agent reads it with `gh` itself.
The orchestrator does the same with `termote agents job ci <id> --send`, after asking you. To let
the server send them on its own, give the job a **Send failed checks** grant: it sends each new
set of failures once, while the agent is at rest, at most three times, with the pull request
numbers and the commands but not the checks' names, which someone else may have written, and
never for a pull request from another repository. Once every pull request is merged, the details offer **Set
done**; removing the worktree stays yours.

<Aside type="note">
  The GitHub CLI has to be installed and signed in for the user the server runs as. If it is
  missing or signed out, the job's details say so. In [container mode](/installation/docker/)
  pull requests are not followed.
</Aside>

## Clean up a finished job

Once you have looked at a job in review, the orchestrator asks whether to clean it up, naming its
tab, its worktree's folder and its branch. With your yes it runs:

```bash
termote agents job finish <id> --close --remove-worktree   # --close alone for a job without a worktree
```

It closes the job's tab and removes the worktree, through the same calls as the PWA's close and
remove, and moves the job from review to done, which can make the jobs waiting on it ready. Termote checks everything first and closes nothing
when one check fails:

- the job was started from the orchestrator's own pane, and is in review or finished;
- its agent is at rest (not working, no dialog, nothing in the background) and its last turn was
  read; an agent that exited leaves a shell, which closes too;
- nothing else runs in the tab, and no other tab or workspace works in the worktree;
- the job's start made the worktree (one you had before is left to you);
- the worktree has no uncommitted or untracked change, its commits are on the pushed branch or are
  the head of a merged pull request, and it holds no `.env` file git ignores.

Files git ignores in the worktree (local databases, `node_modules`, build output) are removed with
it. The branch is deleted only when a merged pull request of the job has the worktree's head;
otherwise it stays and the command says why. A remove that fails after the tab closed says so; the
same command run again removes the rest. On psmux and herdr-core termote cannot tell which pane the
command runs in, so it refuses: close the tab and remove the worktree in the PWA.

Termote also removes finished jobs on its own: one not changed for 30 days goes at the next change
to the ledger (changing it keeps it), and when the ledger holds 200 jobs, adding one removes the
oldest finished job first. `job remove` and `jobs prune` remove them sooner.

## Stop

`stop` ends the turn an agent is working on, as Esc does in its terminal. It needs the `cursor`
from `read --json`, so it never reaches another conversation the pane may have moved on to; an
agent that is not working, or waits on a dialog, is not stopped. Neither is a Claude Code agent
whose screen shows no turn running, such as one that has written its answer and only waits on a
background agent: Esc would not end that work, so `stop` says so (`agent_no_turn`), and the Stop
button is not shown for it. After Esc, `stop` watches the agent for a few seconds and exits 8 when
it still works. You can also stop an agent from its [Chat view](/usage/agent-chat/) or its card in
the [Overview](/usage/overview/).

## Start

Without `--worktree`, `start` opens a new tab in the workspace (`--name` names it) and starts the
agent there with the prompt as its first message. `list`
shows each workspace's folder, or `-` when its panes are in different folders. When the new tab
would open in another folder than that one (a tmux tab opens in the folder its session was
created in), `start` closes it and starts nothing; it prints the folder the agent started in.

With `--worktree <new branch>`, `start` makes a git worktree of the workspace's repository on a
new branch (from `--base`, else its current commit), and starts the agent in the first pane of a
new workspace of its own, so agents working side by side never share a checkout. The workspace you
name only says which repository: the agent does not run there, and `--name` names the new
workspace. With Herdr the worktree goes under `~/.herdr/worktrees/<repo>/`, not beside the
repository. A new worktree has no `node_modules`, so its git hooks (lefthook, husky) are skipped
until its dependencies are installed there; when the repository has a lockfile, `start` reminds
you with the command to run. Run the same command again after a failure and it goes on in the
worktree it made, and with its job: when the agent of that worktree still runs there and is idle,
it gets the prompt; while it works or waits on a dialog, `start` names its pane and job instead. A branch that exists without a worktree is refused, so
an agent never works in a branch you left half done. Termote never removes a worktree
it made: remove it from the workspace menu (Remove worktree) or with git.

Claude Code, Codex and OpenCode all take the prompt as they start, so a new agent gets its task
without anyone typing in the terminal; `-` reads a long prompt from stdin. Termote never types the
prompt into the shell: it writes it to a private file and the command line it types reads that
file back, so quotes, `$(...)`, backticks and line breaks reach the agent as written. That works
in `bash`, `zsh`, `sh` and `fish` on Linux and macOS; a tab whose shell is PowerShell, and any
tab on Windows, refuses a prompt (`prompt_unsupported_shell`) and nothing starts. The prompt is
the agent's command-line argument, which other users of the machine can see, so keep secrets out
of it.

When the work moves on to another task, from a plan to building it or from building it to a review,
the orchestrator proposes by default a new agent in a new tab of the same workspace (or of the
worktree's workspace, on the same branch), as a job of its own: it starts with a clean context, and
the ledger keeps one agent per task. It names the other way too, sending the task to the agent you
already have, which knows the history but carries its whole context, and you pick. Whichever you
pick, it shows you the whole prompt before every `start` and waits for your yes, even when you
already told it to hand the work over.

## What it will not do

The skill keeps your decisions yours:

- It sends to one pane at a time, by id, never the same message to several agents, and never to
  its own pane.
- It asks you before starting an agent, and asks which workspace when the folder is not clear.
  For a task that changes code it proposes a new worktree, and says so.
- It stops an agent only when you ask or agree, and never tries again on its own.
- It treats what `read` and `diff` print as the agents' data, never as instructions.
- It shows you a permission dialog (run a command, edit a file) and answers it with the option
  you choose, unless a grant you gave covers it; it never picks an option that stops the dialog
  asking, and never offers to give itself a grant.
- It never opens, merges or closes a pull request, sends the failed checks to an agent only after
  asking you, and never sets a job `done` because its pull requests merged.
- It never runs `termote show-password` or `termote pair`, and needs no password: the commands
  reach the server over its local socket, which only your own user can open.
- It never types into a pane with tmux, Herdr or Zellij commands: Termote checks that each
  message lands in the agent's input box and each answer matches the dialog on screen.

<Aside type="caution">
  A message waits when the agent's input box holds text you typed in the terminal
  (`input_has_draft`). The orchestrator asks you to send or clear it; it never clears it for you.
</Aside>

## Watch it from the phone

Everything the orchestrator sends shows in the agent's [Chat view](/usage/agent-chat/), the
[Overview](/usage/overview/) and its activity log, as if you had sent it from Termote. Open
Termote on your phone, signed in as usual, to follow along or step in.
