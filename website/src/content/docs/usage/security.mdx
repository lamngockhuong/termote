What Termote protects, what it does not, and what to do when a device is lost. Pairing itself is on
[Pair a Device](/usage/devices/).

## Termote is a remote shell, by design

Whoever signs in with full access has the rights of the OS user that runs the server: they run commands,
read and change files, read the saved password (`termote show-password`), change the configuration
(`termote start --no-auth`) and pair more devices, from the interface or by typing `termote pair` in a
terminal. A device paired from a terminal shows as "Paired with the password, kept when a browser signs
out", like one paired with the password from the CLI. One paired from a browser signed in with the password shows as "Paired from a
signed-in browser" (`termote devices`: `a signed-in browser (<id>)`).

No setting turns a full-access client into something less. The real boundary is the OS user: to limit
what Termote can reach, run it as another user with less access.

## Who can do what

| Signed in as                | Can                                                                                                                                                  |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| The password                | Everything (full).                                                                                                                                   |
| A full device               | Everything the password can, except pairing another full device (it pairs view-only devices only) and signing a password browser out (it only lists them). |
| A view-only device          | Watch the terminal, read the Chat view and Files/Changes inside a git repository (not the home dir, never a file git ignores). It types nothing and changes nothing, but reads everything printed, except the Chat view's tool results of a sensitive file (`.env`, keys). |
| Anyone, with `--no-auth`    | Everything, as soon as they reach the port.                                                                                                         |

## What the server enforces

- It listens on `127.0.0.1` unless started with `--lan`.
- On Linux and Windows (native), a connection made from this machine (any loopback address, or the
  machine's own LAN address with `--lan`) is closed before its first byte is read unless the process at
  the other end runs as the server's OS user, root/SYSTEM, or a user named with
  `--allow-local-user` (a reverse proxy). A connection whose owner cannot be found, or that is no longer
  established, is refused too. On by default; refusals leave `local-user-refused` audit lines (at most one per user every 10 s).
- The CLI reaches the native server over a socket only its own OS user can open (a `0600` Unix socket in
  a `0700` dir, or a named pipe whose ACL names that user and SYSTEM), after checking the server end
  runs as that user or root/SYSTEM. It sends no password there; `termote status` says `Via: socket`.
  Without the socket (the container, an older server) it falls back to TCP and the password.
- Settings > Signed-in browsers and `termote signins` list the browsers signed in with the password (the
  sign-in form, Basic auth, a CLI link); each can be signed out, or every one but the current. A
  sign-out closes that browser's open terminals, one still opening included, drops the pairing codes it
  made, and revokes the devices it paired (and the devices those paired). Logging out of a browser only
  drops its codes. A full device sees the list but signs no one out.
- `termote url --open` (and the Herdr panel) opens the app already signed in: the CLI asks the server
  for a single-use token (30 s), writes it into an HTML page only its user can read (`0600` in a `0700` dir; an owner-only ACL on Windows), and opens that
  page, which posts the token. The token is never in a command line, a URL, the output or the history;
  only a client signed in with the password itself (Basic auth, as the CLI) or over the local socket gets
  one, never a session cookie or a device.
- Every response, a refusal for an unknown host included, also carries `Cross-Origin-Opener-Policy`,
  `Cross-Origin-Resource-Policy` and a `Permissions-Policy` that turns off camera, microphone, location
  and the other device features the app never uses.
- Requests naming an unknown host are refused; writes and the terminal stream must come from the
  Termote page itself, and the stream needs a single-use token.
- Failed sign-ins and wrong pairing codes are rate limited.
- A view-only device is refused every write on the server, not only hidden buttons in the interface.
- With Zellij (`--mux zellij`), what you type and Chat messages reach a pane only through the terminal
  of a Termote Zellij client, never through process arguments, which other local users could read. A
  view-only device watches a Zellij pane through `zellij subscribe`, which cannot type.
- A Content-Security-Policy keeps the page from loading or running code from elsewhere.
- A paired device can carry a time limit (30 days by default when pairing): past it, the device is
  refused and its open terminals close. A device paired by one with a limit never outlasts it.
- Revoking a device also revokes every device it paired. Logging out on a device revokes only that
  device.
- Only the password (a password sign-in, or `termote pair` on the server) pairs a full device.
- Pairing, revoking a device or a sign-in, a device reaching its limit, signing in on the sign-in form or
  with a CLI link, and a refused local connection each leave an `audit:` line in the server log.

## What it cannot prevent

- **A full device used on purpose.** It has a shell: it can read the password, pair devices from a
  terminal, edit the devices file or turn sign-in off. The limits above stop mistakes and clicks in the
  interface, not someone who means it.
- **Secrets printed in a terminal.** A view-only device reads whatever an agent or a command printed.
  The Chat view leaves out a Claude Code tool's result and a Codex edit's diff when they name a
  sensitive file, but not a Grep over a directory, a shell command or a Codex command that prints one.
- **Other services on the same host name.** A cookie is not bound to a port: every service on that name
  receives Termote's cookies. Give Termote a host name of its own.
- **Programs of the same OS user.** Anything else running as that user reads the same files Termote does.
- **Plain HTTP.** Without HTTPS (Tailscale, or a proxy with a certificate), the password and cookies cross
  the network in clear text.
- **The audit lines are not proof.** `termote logs clean`, or any full device, deletes them. Behind a
  proxy (`tailscale serve`) the address they name is the proxy's, loopback.
- **Browser extensions.** An extension allowed on the page reads it and types into it as you. Termote
  cannot tell its input from yours.
- **Port forwarding tools.** VS Code Remote and Dev Tunnels, ngrok or Cloudflare Tunnel forward the port
  from a process of your own user: whoever reaches the tunnel reaches Termote, with only the password in
  the way.
- **Proxies running as root or SYSTEM.** `tailscale serve`, `docker-proxy` and other root proxies are
  trusted (root reads the saved config anyway), so every local user can go through them. On Windows the
  same holds for a session 0 service whose token the server's user cannot read.
- **WSL 2.** Every Windows user reaches a server in WSL 2: in NAT mode through a relay running as root,
  in mirrored mode through a loopback whose client end WSL cannot see, which is let through.
- **macOS.** It does not check which local user makes a connection (that takes `lsof` for each one):
  another user of the Mac has only the password in the way.
- **Another local user slowing the server down.** Looking up who owns a connection reads the
  machine's socket tables once for all the connections waiting, so a flood of connections from
  another user does not multiply that work. It can still slow the server through other means (using
  up ports, CPU); Termote does not promise to stop a local denial of service.
- **The container and `termote serve` configured from the environment.** Neither checks the local user
  of a connection, and the container has no CLI socket.
- **Sessions live in memory.** Restarting the server signs every browser out (devices stay paired).
- **A sign-out ends the cookie, not the password.** A client that sends the password with every request
  (Basic auth) is signed in again at once; change the password for that.
- **What the app keeps on the device.** So that closing the app loses nothing, it keeps in the browser's
  storage the files open in Files and Changes and the unsaved text of files being edited, never a file
  shown as sensitive. Log out removes it, in every tab. A device revoked from elsewhere, or whose session
  ended, still holds it until the app is opened there again or 14 days pass: a file not marked
  sensitive can still hold a secret.
- **Two servers on one state dir** (the service and a `termote serve` started by hand). A revoke in one
  does not close the terminals open in the other; the other refuses the device from its next request.
  Writes to the paired devices take a lock first, so neither brings back a device the other revoked
  (an older release running beside it does not take the lock).

## Recommendations

- Use Termote from the installed PWA, or a browser profile without extensions.
- A reverse proxy running as another OS user needs `termote start --allow-local-user <name>`; until then
  its connections are refused and the log says so.
- Look at Settings > Signed-in browsers (or `termote signins`) from time to time.
- Use HTTPS: `termote start --tailscale <host>` (see [Tailscale](/installation/tailscale/)), or a proxy
  with a certificate.
- Give Termote a host name no other service uses.
- Pair a device view-only unless it must type.
- Keep the default 30-day limit; choose Never only for your own computers.
- Look at `termote devices` from time to time, and revoke what you no longer use.
- Read the `audit:` lines with `termote logs` (native) or `termote container logs` (container).

## If a device is lost

- **A browser signed in with the password:** sign it out in Settings > Signed-in browsers, or
  `termote signins` then `termote signins revoke <id>`. That also revokes every device it paired. If the
  browser is no longer listed (the server restarted, it logged out), find its id in `termote devices`
  (`a signed-in browser (<id>)`) or Settings > Devices, and `termote signins revoke <id>` still revokes
  those devices; if one was full, check what it could have left behind, as below. A device a browser
  paired before 2.0.1 is listed as paired with the password instead, and signing that browser out leaves
  it: revoke it by hand in Settings > Devices or with `termote devices revoke`. If the password itself
  may be known (saved in that browser for Basic auth, written down), run `termote start --fresh` instead.
- **Unsaved text of files.** A full device keeps the files it had open and their unsaved text in its
  browser storage (never a file shown as sensitive), for 14 days after the last edit. Revoking it does
  not remove them: if you get the device back, open the app there and Log out, or clear the site's data
  in the browser.
- **View-only:** revoke it in Settings > Devices or with `termote devices revoke <id>`.
- **Full:** revoke it, then run `termote start --fresh`: it sets a new password, which signs out every
  device and every session. A full device had a shell, so also check what it could have left behind:
  `~/.ssh/authorized_keys`, `crontab -l`, and the service units and login scripts of your user.

## Reporting a vulnerability

Report it privately through [GitHub Security Advisories](https://github.com/lamngockhuong/termote/security/advisories/new),
not in a public issue.
